# LiteSPM Status — Truth Baseline

This file is the **single source of truth for what LiteSPM is**. Every other
document that makes a capability claim must agree with it or link here.

The vocabulary is fixed by
[ARCH/31 §2](ARCH/31-COMPETITIVE-LANDSCAPE-AND-ROADMAP.md#2-evidence-vocabulary-binding-repo-wide).
These six states are distinct and may **not** be collapsed:

| State | Meaning | Minimum evidence |
|---|---|---|
| `DESIGNED` | Specified in an ARCH document. No code implied. | A normative section exists |
| `IMPLEMENTED` | Functions/types exist and are reachable from a package API. | Code compiles; unit tests pass |
| `WIRED` | Reachable from a real user workflow, with real dependencies supplied by production code. | A named non-test caller exists |
| `TESTED` | Covered by an automated test that would fail if the behaviour regressed. | A test asserts the behaviour, not merely that a symbol exists |
| `VERIFIED` | An independent falsifier attempted to break the claim and could not. | Mutation/reproduction evidence |
| `SHIPPED` | Published to users through a real release channel. | A tag, a published artifact, and a live origin serving it |

**Rule.** "Files exist" is at most `IMPLEMENTED`. "Tests exist" is at most
`TESTED`. A component whose only caller is a test is `IMPLEMENTED`, not `WIRED`.
Nothing is `SHIPPED` because it compiles.

Rows below report the **highest honest state** for the user-visible
capability, with the caveat that blocks the next rung. A row that is wired but
whose only real origin is broken is `WIRED` with the breakage stated, not
`SHIPPED`.

### Current release: `rel-2026-10-11-02` (sequence 147, 69,376 capabilities)

Cut 2026-10-11 from the full all-source producer run. Pointer `web/public/v1/current.json`, site
metadata `web/data/release.json`, and the row set `web/data/catalog.json` all describe this release and
were verified to agree with each other (69,376 rows = 48,418 MCP + 20,320 skills + 638 plugins, and the
pointer's `manifestDigest` matches the built manifest).

Sequence 147 rather than 146 exists because the release tree is now **sharded**: at 69,376 rows a
single `listings.json` is 62 MiB, over the 25 MiB per-asset limit Cloudflare Workers enforces at
upload, which is why the site could not be redeployed. Release ids are immutable, so the sharded tree
is a new release rather than a rewrite of the old one (`ARCH/18` §2.1).

**Source completeness: six of seven sources are complete.** `feed:mcpmarket-com` is **incomplete by
budget, accepted deliberately** (decision, 2026-10-11): its crawl is bounded at
`MCPMARKET_MAX_PAGE_FETCHES` pages, and closing it would mean an uncapped crawl of a third-party
directory for rows the official MCP Registry feed already covers. The honest state is published as-is —
`CATALOG_INGESTION_STATUS.incompleteSources: ["feed:mcpmarket-com"]` — and this entry is what stops that
from reading as an accident. A loc refused by our own crawl policy is reported separately as
`refusedLocs` and does not mark a source incomplete (`feed:skills-sh` reports 36).

The release's material change is **installability**: it carries **25,401 `metadata_verified` MCP rows**
from the official MCP Registry, against **zero** in the previous release, where every MCP and skill row
was `discovery_only` and `litespm install <mcp>` could therefore only ever refuse. Verified locally end
to end against a locally built release tree (sync → `install --host codex` → `list` → `install remove`);
the live origin is untouched until this release is deployed.

## Not yet true, and not claimed

**`npm install -g litespm` currently yields a binary that cannot read the published catalog.**
`v0.4.0` was tagged 2h29m before the shard-aware catalog client landed, so the installed binary fails
`catalog sync` with `manifest missing listings.json entry` and therefore cannot `search`, `install`,
or serve `/marketplace`. The source is correct — a build from current `main` syncs 69,376
capabilities — so the gap is release ordering, not code. See §2 `catalog sync` for the full
provenance. **Re-cut the release before treating the npm package as usable.**

Also not yet true: provider **autostart** (a provider row is now written at install time, but
`autostart` stays `0` — starting a process at boot is ARCH/34's decision); **bundle verification in
the npm installer** (the release artifacts themselves are signed as of `v0.4.0` — see §1 Self-update
and §5 — but `npm install -g litespm`'s `postinstall` still verifies by checksum alone,
`SECURITY.md`); `invocation.get` / `invocation.cancel` (an invocation registry); plugin
installation; and any isolation level beyond process supervision.

An agent-driven install **does** complete for skill and MCP-server listings — plan + human approval →
skills ledger / host-config registration — and every attempt, allowed or refused, is written to the
audit log (§1 `audit_events`). The catalog release tree **is** published and the live origin serves
it. Signature coverage reaches the release itself; the remaining trust gaps are the npm installer and
a TUF-style envelope over the catalog.
